Upcasting the Event Log

Stored events are facts that already happened. The code that reads them keeps changing. Upcasting is how both stay true at once — along two independent axes that must be travelled in order.

companion to docs/EventPayloadUpcasterDesign.md · EventTypes · EventPayloadUpcaster

The problem, for anyone new to it

An event-sourced app keeps its history as an append-only log. Every row is a fact that was true when it was written: this conference was planned, at this venue, on these dates. The log is the source of truth — read models are rebuilt from it on every boot.

Which means the log outlives the code. A row written eight months ago holds JSON shaped the way the record looked then. Since then the field became a different type, or a new non-null field appeared, or the class was renamed. Deserializing that old JSON into today's record simply fails.

You have three options, and only one of them is any good. Rewrite history in place, and you lose the property that makes a log trustworthy — plus one bad rewrite corrupts everything. Keep every old version of the class around forever, and the domain model becomes an archaeology exhibit. Or translate on the way in: leave the row alone, and convert what it holds into the current shape as it is read. That translation is upcasting.

A stored row asks two different questions

Three columns matter on every event_log row: the type (a wire id, a string), the schema_version (an integer, or null on the oldest rows), and the payload (JSON). Reading it back raises two questions that have nothing to do with each other — and this codebase answers them with two entirely different mechanisms, drawn in Figures 1 and 2.

The ladder, and why it is version-driven

The structure axis is the part most people mean by "upcasting". Each breaking payload change adds one rung: a small class that advertises the single (type, version) step it consumes and knows how to advance a payload across it. A row climbs from the version it was stamped with to the version the code is on now — no more, no less.

Crucially the composite decides which rung runs from the stored version, not by inspecting the payload. That keeps every rung self-describing and makes a retired rung fail loudly instead of silently skipping a row.

The read path, in order

Put the two axes together (Figure 3) and the whole thing is four steps. The order is not arbitrary: identity resolves first, because the ladder is keyed by the logical name. Until you know which type this row is, you cannot know which rungs it climbs or how far.

One real row, all the way through

Figure 4 traces the oldest kind of row this app holds: a conference written before logical names existed, before datetimes carried a zone, and before the format field. Its schema_version is NULL — it predates the stamp entirely — so it enters the ladder at the bottom and climbs everything.

Stage 2 is the part that sounds mysterious and isn't: it is a map from string to class, and EventTypes is nothing but the setup code that fills it in. register declares a type — it adds the name the app writes today, plus that class's own package-and-name, because that is what the wire id used to be. alias adds one more key for a name the app has stopped writing but the database still holds. Reading a row is then a single lookup.

After that the metadata is fixed. From then on only the payload changes, one rung at a time — stages 3 and 4 show the whole event before and after, with fields the rung didn't touch elided to … — while a local counter tracks how far up the row has come.

What "fails loud" buys you

Every gap in the ladder throws rather than passing a stale payload downstream: an unknown wire id, a missing rung for a step a row still needs, two rungs both claiming the same step. The failure surfaces at boot replay — where the app drops into read-only mode — instead of as a null three screens away in a projector. Stage 5 of Figure 4 is the last of these guards: the record itself refuses to be built from a payload that skipped a rung.

Writing, and making the translation permanent

The write path is the mirror image and needs no cleverness: an append stamps the row with the type's current logical name and current schema version, so a freshly written row is by definition at the top of both axes.

Read-time translation is free but repeated — every boot replay redoes the whole of Figure 4, on every row. The eager migration bakes it in: it runs the read path over the table and writes the result back, so those rows arrive already current next time. Note what it does not rewrite today.

Rules of thumb

When you…You owe…
rename or move an event class nothing — the logical name is what's stored, and it stays put
rename an event's logical name one alias per retired wire id, and every rung's canHandle moved to the new name
change a payload's shape a new rung, a bumped currentSchemaVersion, a fail-loud record, and a golden sample of the old shape
add a brand-new event one register line — version 1, no rungs, nothing to climb

In the code: EventTypes holds the identity axis (register, alias, current version per type). EventPayloadUpcaster is the composite that normalizes the wire id and drives the ladder; each rung implements EventUpcaster. LegacyEventMigration is the write-back pass.

The worked example throughout is ConferencePlanned — the only type past version 2, and the only one to have been renamed, so it exercises both axes at once.
